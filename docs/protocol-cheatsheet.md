# Codex app-server — protocol cheatsheet (from generated TS bindings)

Source of truth: `codex-remote/protocol/` — 760 files generated by [ts-rs] from the Rust
`app-server-protocol` crate: `index.ts` (root namespace, 95 root types), `v2/index.ts`
(re-exports all 664 `v2` types), `ClientRequest.ts`, `ClientNotification.ts`,
`ServerNotification.ts`, `ServerNotificationEnvelope.ts`, `ServerRequest.ts`.
Every type name below is a real file in that tree. Counts: **109** client→server request
methods, **87** server→client notification methods, **10** server→client requests.

---

## 1. Transport & envelope

The bindings describe four message kinds. Quoted shapes (verbatim key sets):

```ts
// ClientRequest.ts  — client -> server request (109 variants, this one leads the union)
{ "method": "initialize", id: RequestId, params: InitializeParams }
// ...every variant has exactly the members: method, id, params

// ClientNotification.ts — the ENTIRE client -> server notification union
export type ClientNotification = { "method": "initialized" };

// ServerNotification.ts — server -> client notification (87 variants), NO id
{ "method": "error", "params": ErrorNotification } | { "method": "item/completed", "params": ItemCompletedNotification } | ...

// ServerNotificationEnvelope.ts — what the app-server actually emits (adds a timestamp)
export type ServerNotificationEnvelope = { emittedAtMs?: number, } & ({ "method": "error", "params": ErrorNotification } | ... );

// ServerRequest.ts — server -> client request (10 variants, same {id, method, params} shape)
{ "method": "item/commandExecution/requestApproval", id: RequestId, params: CommandExecutionRequestApprovalParams }
```

Facts a browser client must not get wrong:

- **No `jsonrpc` member.** A grep of all 760 generated files for `jsonrpc` returns **zero**
  matches. This is *not* JSON-RPC 2.0 framing: there is no `"jsonrpc": "2.0"` field on
  requests, notifications or (inferred) responses. Shape is
  `{id, method, params}` → `{id, result}` / `{id, error}` and `{method, params}` for
  notifications. (Caution: the on-disk desktop bundle
  `desktop-webview/webview/assets/app-initial-*.js` *does* contain `jsonrpc: "2.0"` zod
  schemas — those are **MCP** client/server schemas, not app-server framing. Don't copy them.)
- `id`: `RequestId = string | number`.
- `params` is **omitted** for a set of methods declared `params: undefined`:
  `account/logout`, `config/mcpServer/reload`, `configRequirements/read`,
  `windowsSandbox/readiness`, `account/workspaceMessages/read`,
  `account/gatewayOAuth/read|login|cancel`, `externalAgentConfig/import/readHistories`;
  and optional (`params?:`) for `account/rateLimits/read`, `account/usage/read`.
- **Responses are not modelled.** There is no `ServerResponse` / `JSONRPCResponse` type file
  in the tree; only `*Response.ts` payload types exist. The client correlates by `id` and
  should accept both `{id, result}` and an error form carrying `code`/`message`/`data`.
  This is the single detail to confirm against a live server before shipping.
- Notifications never carry `id`; every server notification carries an object `params`, and
  `emittedAtMs` (unix ms) is present on current servers ("Optional so clients can decode
  notifications from older app-server versions").
- v2 method names are namespaced with `/` and are **not** automatically v2-prefixed: the
  wire method for `ThreadStartParams` is literally `thread/start`. Note `threadSection/*`
  (not `thread/section/*`) for section CRUD, while `thread/section/move` uses a slash.

## 2. Handshake

Method string: **`initialize`** (root namespace, not `v2`).

```ts
// InitializeParams.ts
export type InitializeParams = { clientInfo: ClientInfo, capabilities: InitializeCapabilities | null };

// ClientInfo.ts
export type ClientInfo = { name: string, title: string | null, version: string };

// InitializeCapabilities.ts
export type InitializeCapabilities = {
  explicitGatewayOauth?: boolean,
  experimentalApi: boolean,            // REQUIRED
  requestAttestation: boolean,         // REQUIRED
  mcpServerOpenaiFormElicitation?: boolean,
  optOutNotificationMethods?: Array<string> | null,   // exact method names, e.g. "thread/started"
  extensions?: { [key in string]?: JsonValue } | null,
};

// InitializeResponse.ts
export type InitializeResponse = {
  userAgent: string,
  codexHome: AbsolutePathBuf,   // absolute path to the server's $CODEX_HOME
  platformFamily: string,       // e.g. "unix" | "windows"
  platformOs: string,           // e.g. "macos" | "linux" | "windows"
};
```

`initialized` notification: `ClientNotification` has exactly one variant,
`{ "method": "initialized" }` — no `id`, no `params`. The types do not enforce ordering, but
this variant exists solely for the post-`initialize` handshake step, so send it immediately
after the `initialize` response resolves, before any `thread/*` call.

`optOutNotificationMethods` is the cheapest bandwidth win for a browser client: pass the
exact notification method names you don't render (it is honoured per-connection).

### 5c. Decision enums (exact members)

```ts
type CommandExecutionApprovalDecision =
  "accept" | "acceptForSession"
  | { "acceptWithExecpolicyAmendment": { execpolicy_amendment: ExecPolicyAmendment } }
  | { "applyNetworkPolicyAmendment": { network_policy_amendment: NetworkPolicyAmendment } }
  | "decline" | "cancel";

type FileChangeApprovalDecision = "accept" | "acceptForSession" | "decline" | "cancel";

// legacy, still used by execCommandApproval / applyPatchApproval
type ReviewDecision =
  "approved" | "approved_for_session" | "approved_mcp_policy_amendment"
  | { "approved_execpolicy_amendment": { proposed_execpolicy_amendment: ExecPolicyAmendment } }
  | { "network_policy_amendment": { network_policy_amendment: NetworkPolicyAmendment } }
  | { "denied": { rejection: string } }        // note: "denied" carries a reason
  | "timed_out" | "abort";
```

Note the naming split: v2 uses `accept`/`decline`/`cancel`, the legacy root approvals use
`approved`/`denied`/`abort`/`timed_out`. Do not mix them. Surface **all four** UI actions
(accept, accept-for-session, decline, cancel) — `cancel` is what you send when the user
dismisses the dialog, and `timed_out` may arrive via `serverRequest/resolved` instead.

### 5d. Two more server requests

## 7. `experimentalApi` / capability gating

- `InitializeCapabilities.experimentalApi` — *"Opt into receiving experimental API methods
  and fields."* Default to `true` for a new client or you will not see the gated methods /
  fields. `requestAttestation` gates only `attestation/generate`
  (*"Opt into `attestation/generate` requests for upstream `x-oai-attestation`"*).
- Types whose own doc comment says EXPERIMENTAL (i.e. gated): `PlanDeltaNotification`,
  the whole `app/*` family (`AppsListParams`, `AppsListResponse`, `AppsReadParams`,
  `AppsReadResponse`, `AppInfo`, `AppSummary`, `AppBranding`, `ConnectorMetadata`,
  `AppToolSummary`), `AppListUpdatedNotification`, `CollaborationModeMask`,
  `ToolRequestUserInputParams` / `ToolRequestUserInputQuestion` /
  `ToolRequestUserInputOption` / `ToolRequestUserInputAnswer` /
  `ToolRequestUserInputResponse`, the whole `thread/realtime/*` set
  (`ThreadRealtimeItem`, `ThreadRealtimeAudioChunk`, `ThreadTimelineEntry`, ...).
- `sandbox` in `ThreadStartResponse` / `ThreadResumeResponse` / `ThreadForkResponse` is
  documented as *"Legacy sandbox policy retained for compatibility. Experimental clients
  should prefer `activePermissionProfile`"*, and `ActivePermissionProfile` is
  `{ id: string, extends: string | null }` — but **none of those responses carries that
  field**; fetch profile provenance elsewhere (e.g. `permissionProfile/list`).
- Methods that are experimental by name: `experimentalFeature/list`,
  `experimentalFeature/enablement/set`, `permissionProfile/list`,
  `modelProvider/capabilities/read`.
- `explicitGatewayOauth` applies to the whole app-server gateway runtime for the process:
  "later connections cannot undo it" — set it only on the first connection.
- `extensions` / `mcpServerOpenaiFormElicitation` are MCP-extension opt-ins; irrelevant to
  text chat.
- `optOutNotificationMethods` (`Array<string> | null`) suppresses exact notification method
  names per connection (doc example: `thread/started`).

## 8. Practical gotchas

1. `Thread.turns` is empty except on `thread/resume`, `thread/fork`, and
   `thread/read` when `includeTurns: true`. For long threads use
   `thread/turns/list` + `thread/items/list`, seeded by the `turnsBackwardsCursor` /
   `itemsBackwardsCursor` returned by `thread/resume`.
2. Every list response is cursor-paginated with both `nextCursor` and `backwardsCursor`;
   pass `backwardsCursor` with the reversed `sortDirection` to catch updates to the anchor
   page.
3. `turn/steer` requires `expectedTurnId` and fails if it does not match the live turn —
   re-read the active turn id from `turn/started`/`thread/status/changed` before steering.
4. `input` for `turn/start` and `turn/steer` is `UserInput[]`, never a bare string, and
   `text` inputs must carry `text_elements: []`.
5. `thread/start` has **no required params** — `{}` is valid; the server picks model, cwd
   and sandbox defaults, which come back in `ThreadStartResponse`.
6. One `id` space: use string ids for requests; `RequestId = string | number` and the same
   type appears in `serverRequest/resolved`, so keep a map `requestId -> dialog`.
